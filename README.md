# 温室灌溉决策服务

把**分区/作物生育期、传感器质量、蒸散估算、水肥配方**组织成可追溯灌溉计划的 Python 决策服务。
纯标准库实现（Python ≥ 3.11），SQLite 持久化，重启后从同一计划继续。

## 要解决的问题

连续高温下，土壤探头存在**延迟补报**：按“最新一条接收读数”开阀，常把已经浇过的畦面再次灌水，
同时园区当天取水额度不可突破。本服务的核心约定：

1. **遥测以业务发生时间 `occurred_at` 为准，不以接收顺序为准**。乱序、迟到、重复事件都安全。
2. **灌溉栅栏（wet fence）**：最近一次灌溉结束前的读数（含灌溉进行中、入渗未完成的读数）一律排除，
   不可能用“浇前/浇中”的干读数触发二次灌水。
3. **发布后的迟到读数只重排尚未开始的时段**；正在浇与已结算的时段不动、不重扣。
4. **阀门命令有确定 `command_uid`，台账以时段为幂等键**：回执重复只计数，网关失联重投同一 uid，
   均不会二次扣水。
5. **人工停灌立即压过自动指令**：已开阀立即发关阀令，停灌期间不再自动开阀。
6. **配额按园区本地日（Asia/Shanghai）分账，跨午夜时段按日拆分**，任一日净额不突破日限额。

## 运行

```bash
# 校验资料包 + 全部场景测试
python -m unittest discover -s tests

# 启动服务（默认 0.0.0.0:8080，后台每 10s tick，启动先 reconcile）
python -m irrigation serve --db data/irr.db --reference reference/domain.json --port 8080

# 用系统 cron 替代内置调度也可以
python -m irrigation tick --db data/irr.db --reconcile
```

## 决策口径（为何浇、浇多少）

每个分区每个计划日记录完整的判定链（看板 `zones[].why` 可追溯）：

- **墒情融合** `engine.fuse_readings`
  - `good`：取最新一条有效 good（12h 新鲜窗）；
  - `suspect`：与最近 good 做 0.3 收缩加权，无 good 佐证时标注降级，且不得单方加大剂量；
  - `offline`/超期：转蒸散水量平衡后备。
- **水量平衡** `ETc = kc(stage) × ET0`，自最近 good 读数（墒情校准锚点）按实际时间比例积分，
  扣除已确认灌溉的实测水深；预计亏缺越过 `允许亏缺线 = dep_max × TAW` 才补水。
- **剂量**：good 取墒情口径与水量平衡的较大者；suspect 需显著更高（+10%）才采纳墒情口径；
  offline 只走水量平衡。
- **水肥配方**随计划标注（如番茄坐果期 N/P/K、EC），仅作执行配比，不参与水量守恒。
- **排程**：按额定流量换分钟数，同一 `shared_line` 阀门绝不重叠（并发约束），
  受灌溉窗口与各本地日剩余额度双重约束；排不下的水记 `unscheduled_l` 缺口，不静默超排。

## 计划生命周期与接口

发布前农艺师可反复修订阈值、ET0、窗口并**预演（不落库、不占额）**；发布即写预留台账。
修订重新发布时，旧版未执行时段取消退额，已开始执行/已结算时段并入新版，旧计划标 `superseded`。

| 方法/路径 | 说明 |
|---|---|
| `POST /telemetry` | 接入遥测（乱序/重复安全）；新读数触发当日在线重排 |
| `POST /plans/preview` | 预演，不写库不占额 |
| `POST /plans/drafts` | 生成/替换当日草案 |
| `POST /plans/{id}/publish` | 发布（写预留） |
| `POST /plans/revise` | 修订阈值/ET0/窗口并重新发布 |
| `GET  /plans?day=` / `GET /plans/{id}` | 计划明细（含判定理由、配方） |
| `POST /tick` | 到期开阀/到点关阀/窗口过期退额/失联重投 |
| `POST /reconcile` | 重启对账，待确认命令按同一 uid 重投 |
| `POST /commands/{uid}/ack` | 阀门回执（重复回执幂等，不二次扣水） |
| `POST /entries/{id}/resolve` | 人工处置失联关阀：`measured` 按实测结算 / `abort` 退额 |
| `POST /pause` / `POST /resume` | 人工停灌（全局或分区，立即关阀）/ 恢复 |
| `GET  /dashboard?day=` | 各区**为何浇**、各日**剩余额度**、**待确认命令**、告警 |
| `GET  /ledger?day=` | 水量台账流水 |

请求体可带 `"now": "ISO8601"` 注入时钟，便于预演与测试。

## 水量守恒模型

台账（`ledger`，按本地日）三类流水，均以时段 id 为幂等键：

| 种类 | 方向 | 时机 |
|---|---|---|
| `reserve` | + | 计划发布/重排新增时段 |
| `release` | − | 取消、窗口过期、人工中止、结算冲销预留 |
| `consume` | + | 关阀回执按**实测过流**结算（无实测按额定×时长） |

```
日已占用 = reserve − release + consume ≤ daily_water_limit_liters
```

结算先写 `release(−计划量)` 再写 `consume(+实际量)`，净额即实际量；
跨午夜时段按开→关的实际秒数比例拆分到两个本地日，分天合计严格等于实测总量（尾差并入首日）。

## 场景核对

`tests/test_scenarios.py` 覆盖：

- **跨午夜配额**：夜间窗口 23:00–01:00，跨日拆分合计 == 实测，两天各自不超限；
- **并发开阀**：共线 `L-A` 两个阀门时段严格不重叠，且总量受日配额截断、缺口显式上报；
- **传感器降级**：乱序旧读数不覆盖新读数；suspect 收缩融合；掉线走水量平衡且不额外加水；
  灌溉前/灌溉中读数进排除清单；
- **幂等与失联**：重复关阀回执只结算一次；网关断连后 reconcile 用同一 uid 重投，台账不新增；
- **人工停灌**：立即关阀、停灌期不自动开、窗口过期自动退额，净额只剩实测 600 L；
- **迟到读数**：只取消未开始时段并退额，已结算水量不变；
- **重启续跑**：新进程从同一计划继续，待确认命令重投，结算水量不重扣。

## 对接真实硬件

实现 `irrigation.service.Gateway.send(command)`（PLC/物联网平台），**网关侧也必须以
`command_uid` 去重**；关阀回执在 `result.liters` 回填实测过流升数，服务即按实测结算。
无实测时按阀门额定流量 × 实际开阀时长估算并标注 `settle_source=rated`。
